# Hardware assumptions to confirm

Each item is something the firmware or the wiring relies on that has **not** been verified on the real hardware.
Please report each result back on the ticket (value, photo or "confirmed"). Items marked **before wiring** must be
settled before anything is soldered.

| # | Assumption | Why it matters | How to check | Status |
|---|---|---|---|---|
| H1 | **before wiring**: the Liter Energy 902025 cell has a **protection circuit (PCM)** (over-discharge, over-charge, short) | The XIAO has no visible discharge cut-off (`feasibility.md` §4). Without a PCM, a deep discharge can ruin the cell or make it unsafe | Look for a small PCB under the cell's tape/kapton at the lead end; check the seller's datasheet for "PCM"/"PCB protection"; a protected cell often measures 0 V when its PCM has tripped and recovers on charge | open |
| H2 | **before wiring**: the cell accepts **≈ 200 mA** charge current (0.5 C) | The XIAO's SGM40567 charger is set to 200 mA by R9 = 120 kΩ (schematic sheet 03) and cannot be changed in firmware | Cell datasheet: "standard charge" / "max charge current". If it is below 200 mA, do not use this cell with this board | open |
| H3 | **before wiring**: the Elegoo RGB LED is **common cathode**; its forward voltages are about 1.8–2.0 V (red) and 2.6–2.9 V (green/blue) at 1–2 mA | Polarity selects `APP_LED_COMMON_CATHODE`; Vf sets the resistor values in `wiring.md` | Multimeter in diode mode (red probe = +): black probe on the long leg, red probe on each other leg. If each colour glows faintly, the long leg is the cathode (**common cathode**). If nothing glows that way but it glows with the red probe on the long leg and the black probe on each colour leg, it is **common anode**. Report the polarity and each colour's reading in V | **confirmed: common cathode** (operator, 2026-11-22: long leg on GND lights the LED). Vf not measured; the red resistor is now 220 Ω (`wiring.md`) |
| H4 | PD03 (`VBAT_CTL`) only switches the battery divider (HIGH = on), and does **not** enable/disable the charger | The Arduino core calls PD3 "Battery charger enable", the schematic `VBAT_CTL`. Phase 4 must know before driving it | Phase 4 bench test: USB + battery connected, charging (red LED flashing); flash the Phase 4 test build that toggles PD3 every 10 s; the CHARGE LED must keep flashing. Report what the LED does | open (Phase 4) |
| H5 | With USB plugged in, the XIAO powers the lamp from USB while charging the cell (load sharing via D1/U6) | Decides whether the lamp may be used while charging and how battery readings behave | Phase 4: measure the battery current with USB plugged in and the LED on (multimeter in series in the red lead): it should be positive (charging) | open (Phase 4) |
| H6 | The radio reaches the **on-board chip antenna** with the RF switch pins PB04/PB05 left in their reset state (as the Arduino core does) | Wrong state = weak or no Zigbee link | Phase 3, no reflash: lamp joined, at a fixed distance from its parent; for each of `zigbee rfswitch reset`, `0`, `1`: send a few commands from Z2M, then `zigbee status` and note the parent LQI/RSSI (and the LQI in Z2M). `bench-test.md` §3.6 | open (Phase 3). Sources: PB05 = switch power, PB04 = select "0: RF1, 1: RF2"; which one is the chip antenna is not documented (`feasibility.md` §6) |
| H7 | The board has a **Gecko bootloader** at `0x08000000–0x08005FFF`, so an application linked at `0x08006000` boots | If that area is empty, the app does not start (the board stays recoverable over SWD) | After the backup in `flashing.md` step 2: `xxd -l 64 xiao_mg24_backup_*.bin`. | H8 | **before the first plug-in**: the cell's + reaches **BAT+** through the JST plug and the pigtail.
